# 관리자웹 개선 요청 검토 및 반영 계획

작성일: 2026-08-12

구현 상태: 0~4단계의 백엔드와 관리자웹 반영 완료. 실제 모바일 앱 UI는 저장소에 앱 구현체가 없어 API 계약까지만 제공한다.

## 결론

- 기술적으로 영구 구현 불가능한 항목은 없다.
- 다만 **9번 `테스트리더`는 요구사항 의미가 불명확하여 현재 계획에 넣을 수 없다.** 한 문장 수준의 목적과 사용자를 먼저 확정해야 한다.
- 4번과 5번의 핵심인 사용자·판매자 인증·스토어 상태 관리는 이미 관리자 UI와 API에 일부 구현되어 있다.
- 6번 페이지네이션과 7번 서버 검색·필터는 데이터 증가 전에 우선 반영해야 한다.
- 1번, 10번, 11번은 각각 만들지 않고 하나의 **고객지원/문의 티켓 기능**으로 통합한다.
- 8번은 현재 코드에서 테마 버튼과 로그아웃 진입점이 분리되어 있어 별도 수정이 불필요하다. 실제 배포 화면이 다르면 배포 버전 또는 대상 화면을 다시 확인한다.
- 관리자에게 임의 DB 수정 권한을 노출하거나 사용자를 즉시 `탈퇴` 상태로 바꾸는 기능은 반영하지 않는다. 승인된 업무 액션과 감사 이력으로 제한한다.

| 12 | FAQ 탭 | 가능 | FAQ 작성·정렬·공개 상태·대상 앱 관리와 앱 조회 API를 추가한다. 문의 기능 안정화 후 우선순위로 둔다. |

## 반영하지 않을 것

### 관리자 직접 DB 편집

관리자웹에는 테이블/컬럼을 임의 수정하는 기능을 만들지 않는다. 대신 아래처럼 서버가 검증하는 명시적 액션만 제공한다.

- 사용자 이용정지/복구
- 판매자 인증 승인/반려
- 스토어 운영정지/복구
- 플랫폼 공지 게시/숨김
- 문의 담당/답변/종료
- FAQ 게시/숨김/정렬

각 액션에는 관리자 ID, 대상, 변경 전후 값, 사유, 처리 시각을 감사 로그로 남긴다.

### 관리자 즉시 탈퇴 처리

현재 사용자 도메인은 탈퇴 요청 후 7일 유예, 토큰 무효화, 확정 시 이름·연락처·이메일·비밀번호·역할 정리를 수행한다. 단순 상태 변경 API로 `WITHDRAWN`을 지정하면 이 절차를 우회할 수 있으므로 다음 원칙을 적용한다.

- 관리자 UI에서 `탈퇴`는 조회/필터 상태로만 제공한다.
- 관리자 상태 변경 API는 `ACTIVE`, `SUSPENDED`만 허용한다.
- 운영상 강제 탈퇴가 꼭 필요해지면 사유, 재인증, 개인정보 정리, 감사 이력을 포함한 별도 유스케이스로 설계한다.

## 권장 관리자 메뉴 구조

```text
대시보드
회원 관리
  - 구매자 회원
  - 판매자 회원·인증
스토어 관리
콘텐츠 관리
  - 플랫폼 공지
  - FAQ
고객지원
  - 문의 목록
운영 설정 (실제 설정 항목이 생길 때만 노출)
프로필 메뉴
  - 내 계정
  - 로그아웃
```

`판매자앱/구매자앱 관리`라는 표현보다는 관리 대상이 명확한 `구매자 회원`, `판매자 회원·인증`, `스토어 관리`를 권장한다. 앱 자체 설정이나 버전 관리가 추가될 때만 별도의 `앱 관리` 메뉴를 만든다.

## 단계별 반영 계획

### 0단계 — 상태 변경 안전장치

대상: 4, 5

- 관리자 사용자 상태 API에서 `ACTIVE`, `SUSPENDED`만 허용한다.
- 자기 계정 정지 방지 규칙을 유지한다.
- 상태 변경 사유 입력과 감사 로그의 최소 스키마를 정한다.
- 사용자 상태에 `탈퇴 대기`와 `탈퇴`를 구분해 표시한다.

완료 조건:

- API를 직접 호출해도 `WITHDRAWAL_PENDING`, `WITHDRAWN`으로 단순 변경할 수 없다.
- 허용/거절 전이가 통합 테스트로 검증된다.

### 1단계 — 대용량 목록 기반 정리

대상: 2, 6, 7

- 사용자·판매자·스토어 목록 API를 `page`, `size`, `sort`, `query`, `status`, `role/verificationStatus` 조건을 받는 페이지 응답으로 변경한다.
- 현황 수치는 전체 엔티티 로딩 대신 DB 집계 쿼리로 계산한다.
- 관리자 메뉴를 구매자, 판매자/인증, 스토어로 분리한다.
- 검색은 입력 지연(debounce) 후 서버에 요청하고, 필터 변경 시 첫 페이지로 이동한다.
- URL 쿼리에 현재 탭·검색·필터·페이지를 보존해 새로고침과 공유가 가능하게 한다.

권장 필터:

- 구매자/판매자 회원: 전체, 활성, 이용정지, 탈퇴 대기, 탈퇴
- 판매자 인증: 전체, 대기, 인증, 반려
- 스토어: 전체, 활성, 운영정지, 폐점

완료 조건:

- 목록당 기본 20건만 조회한다.
- 검색·필터·페이지 이동을 조합해도 전체 결과 기준으로 정확하다.
- 상태 변경 후 현재 조건과 전체 현황 수치가 다시 동기화된다.

### 2단계 — 플랫폼 공지

대상: 3

- 스토어 공지와 분리된 `platform_announcements`를 추가한다.
- 대상 채널은 `CUSTOMER_APP`, `SELLER_APP`, `ALL`로 둔다.
- 초안/게시/숨김, 게시 시작·종료, 제목·내용, 작성/수정 관리자 정보를 관리한다.
- 관리자 CRUD API와 각 앱의 게시 공지 조회 API를 추가한다.
- 앱 홈 또는 알림 영역의 노출 위치를 제품 결정으로 확정한다.

완료 조건:

- 관리자가 대상 앱과 게시 기간을 지정할 수 있다.
- 각 앱에는 현재 게시 기간이고 대상이 일치하는 공지만 노출된다.

### 3단계 — 고객지원 문의 MVP

대상: 1, 10, 11

- 주문 채팅과 분리된 `support_tickets`, `support_messages`를 추가한다.
- 요청자 유형은 구매자/판매자, 문의 카테고리는 계정/스토어 노출/주문·결제/기타로 시작한다.
- 상태는 접수, 답변 대기, 사용자 응답 대기, 종료로 관리한다.
- 앱 문의 작성/목록/상세 API와 관리자 문의 목록/상세/답변 API를 만든다.
- 관리자 화면에서 요청자 유형, 상태, 카테고리, 기간으로 검색·필터한다.
- 초기 버전은 저장형 메시지 스레드와 새 답변 알림으로 충분하며, 운영 필요가 확인되면 WebSocket 실시간 갱신을 추가한다.

완료 조건:

- 구매자와 판매자가 자기 문의만 조회·작성할 수 있다.
- 관리자는 전체 문의를 조회하고 답변·상태 변경할 수 있다.
- 주문 채팅 데이터와 고객지원 문의가 섞이지 않는다.

### 4단계 — FAQ

대상: 12

- `faqs`에 대상 앱, 카테고리, 질문, 답변, 노출 순서, 게시 상태를 둔다.
- 관리자 작성/수정/정렬/게시 API와 앱 공개 조회 API를 만든다.
- 문의 작성 화면에서 카테고리에 맞는 FAQ를 먼저 제안해 중복 문의를 줄인다.

완료 조건:

- 앱별·카테고리별 공개 FAQ만 노출된다.
- 관리자가 노출 순서를 바꾸고 즉시 게시/숨김할 수 있다.

## 테스트 및 검증 범위

- 백엔드: 역할별 접근 제어, 상태 전이, 페이지 경계, 복합 필터, 탈퇴 상태 보호, 공지 노출 기간, 문의 소유권 테스트
- 관리자웹: 탭/검색/필터/페이지 상태, 상태 변경 후 재조회, 권한 오류, 빈 목록과 로딩 상태 테스트
- 앱: 대상별 공지·FAQ 노출, 문의 작성/답변 확인, 다른 사용자의 문의 접근 차단 테스트
- 운영: 목록 쿼리 실행 계획과 인덱스 확인, 관리자 변경 감사 로그 확인

## 착수 전 확인할 한 가지

9번 `테스트리더`가 다음 중 무엇인지 원문 작성자에게 확인한다.

- 테스트 계정/테스터 그룹 관리
- 테스트 결과를 읽는 리포트 화면
- 스크린리더 접근성 테스트
- 그 밖의 별도 기능명

정의가 확인되기 전에는 일정과 데이터 모델을 잡지 않는다.
