# POPQ 판매자 채널 현황 및 2026-07-30 인계 리포트

작성 기준: 2026-07-29  
대상: Flutter 판매자 앱, React 판매자 웹, Spring Boot 공통 API

## 1. 결론

- Flutter 판매자 앱은 `대시보드·운영·주문·고객·매출` 정보구조와 실제 인증·사업장·주문·상품 가용성·매출 API 연결 기반을 갖췄다.
- React 판매자 웹은 주문·상품 생성/옵션·QR·환불·매출 차트·스토어 설정·관리자 화면까지 Flutter보다 넓은 운영 기능을 제공한다.
- 두 클라이언트는 동일한 Spring Boot와 MySQL을 원본으로 사용하므로 주문, 상품, 영업 상태, 매출 데이터는 기능적으로 연동할 수 있다.
- 현재 즉시 완전 연동된 상태는 아니다. React 웹은 수동 `storeId + Access Token` 연결, Flutter는 개발 SELLER 로그인과 보안 세션을 사용하며 실시간 방식도 웹 STOMP, Flutter REST 재조회로 다르다.
- UI는 POPQ의 라임·코랄·크림 계열 브랜드 방향은 호환되지만 React CSS와 Flutter Material 3가 별도 구현이므로 컴포넌트 수준의 동일 UI는 아니다.
- 공지사항과 고객 메시지는 양쪽 모두 서버 저장·조회 계약이 없다. Flutter에는 올바른 화면 위치와 빈 상태만 있으며 실제 관리 기능은 미구현이다.

## 2. Flutter 판매자 앱 현황

| 영역 | 현재 구현 | 남은 차이 |
|---|---|---|
| 인증·보안 | 판매자 전용 보안 저장 키, 세션 복원, `/auth/me` 역할 재검증, CUSTOMER 세션 차단, 개발 SELLER 로그인 | Firebase Authentication, Refresh Token 갱신, 운영 계정 로그인 |
| 대시보드 | 전체 사업장 목록, 현재 선택 표시, 일반 매장·행사 판매점 신규 등록, 사업장 선택·유지 | 사업장 주소·태그·좌표 재편집, 사업자 인증 상태 |
| 운영정보 | 선택 사업장 정보, OWNER/MANAGER 영업 상태 변경, STAFF 읽기 전용 | 사업장 상세 수정, 운영 시간, 테이블·QR, 직원·권한 |
| 공지사항 | `운영 > 공지사항` 위치와 빈 상태 | 엔티티·API·작성·예약 게시·채널별 노출 |
| 메뉴 관리 | 상품 검색·상태 필터, 품절, 고객 앱 판매, QR 웹 판매 | 카테고리 생성·정렬, 상품 생성·수정, 가격·이미지, 옵션 편집, 판매 시간 |
| 주문 관리 | 사업장별 목록·상태 필터·상세·버전 동기화, 접수·거절·준비·준비 완료·완료 | 결제 상세·환불 UI, 실시간 신규 주문 수신, 주문 이력 표현 강화 |
| 고객 | `고객` 탭과 메시지 없음 상태 | 대화 목록·상세·읽음·답장·차단·신고·보존 정책 |
| 매출 | 전체 사업장 합계, 사업장별 실적, 일·월 범위, 메뉴별 매출 | 일별 차트, 취소·환불·순이익, 사용자 지정 기간, 정산·내보내기 |
| 알림 | 주문 REST 동기화 기반 | 판매자 FCM 토큰 등록·푸시 수신·딥링크 |

판매자 앱의 모든 주문·상품·매출 요청은 사업장 ID를 포함한다. 서버는 플랫폼 SELLER/ADMIN 역할과 활성 StoreMember, 주문·상품의 사업장 소속을 다시 검증한다. 고객 앱과 판매자 앱은 application ID, 보안 세션 키, 앱별 저장소가 분리되어 있다.

## 3. React 판매자 웹 현황

| 웹 화면 | 실제 기능 | Flutter와 관계 |
|---|---|---|
| 주문 운영 | 상태별 보드, 상세, 접수·거절·준비·완료, 결제 요약, 전액 환불, STOMP 신규 주문 | 핵심 주문 상태는 공유. 환불·STOMP는 웹에만 구현 |
| 상품 관리 | 카테고리 생성, 상품 생성, 옵션 그룹 전체 편집, 품절, QR/고객 앱 채널 | Flutter는 현재 가용성 변경만 구현 |
| QR 관리 | 테이블 QR 조회·발급·저장·활성/비활성/폐기 | Flutter 미구현 |
| 매출 분석 | 7일·30일 지표, 일별 차트, 이용 유형, 인기 상품 | 같은 매출 API 사용. Flutter는 전체 사업장 일·월 요약 |
| 스토어 설정 | 영업 상태, 운영 정보, 테이블 추가 | 영업 상태 공유. Flutter는 사업장 등록·선택을 추가 제공 |
| 관리자 운영 | 사용자·판매자 인증·스토어 상태 | Flutter 판매자 앱 범위 밖 |
| 연결 설정 | 데모 또는 수동 Store ID·Access Token | 운영용 로그인 UX가 아니며 공개 전 교체 필요 |

웹의 현재 하단/사이드 정보구조는 `주문·상품·QR·매출·설정·관리자`이고 Flutter의 `대시보드·운영·주문·고객·매출`과 다르다. 역할과 사용 환경이 다르므로 레이아웃 자체를 동일하게 만들 필요는 없지만, 기능 명칭·상태 라벨·색상 토큰·API 오류 문구는 통일할 수 있다.

## 4. 웹–앱 연동 가능성

| 계약 | 가능 여부 | 현재 상태와 주의점 |
|---|---|---|
| 동일 사업장 주문 조회·상태 변경 | 가능 | 한쪽 변경은 DB에 저장되고 다른 쪽 REST 재조회 시 반영 |
| 상품 품절·채널 노출 | 가능 | 동일 availability API 사용 |
| 영업 상태 | 가능 | 동일 business-status API 사용 |
| 매출 | 가능 | 동일 analytics API 사용. 웹은 선택 사업장, 앱은 사업장별 호출 후 합산 |
| 사업장 목록 | 가능 | 동일 `/seller/stores` 사용 |
| 사업장 신규 등록 | 부분 가능 | Flutter 연결 완료, 웹 등록 UI 없음 |
| 상품·카테고리·옵션 전체 편집 | 부분 가능 | 웹 연결 완료, Flutter UI 미구현 |
| 결제 요약·환불 | 부분 가능 | 웹 연결 완료, Flutter UI 미구현 |
| QR·테이블 | 부분 가능 | 웹 연결 완료, Flutter UI 미구현 |
| 실시간 주문 | 부분 가능 | 웹 STOMP 연결, Flutter FCM 미연결 |
| 공지사항 | 불가 | Spring API와 DB 계약 없음 |
| 고객 메시지 | 불가 | Conversation/Message API와 원본 저장 방식 미확정 |
| 동일 인증 UX | 불가 | 웹 수동 연결, Flutter 개발 로그인. 각 운영 인증을 별도 완성해야 함 |
| 동일 UI 컴포넌트 | 직접 공유 불가 | React DOM/CSS와 Flutter Widget 차이. 디자인 토큰과 UX 계약만 공유 가능 |

따라서 “기능적으로 모두 연동 가능”은 공통 API가 이미 있는 영역에 한해 맞다. “UI적으로 모두 연동”은 동일 코드를 공유한다는 의미로는 불가능하고, 디자인 토큰·내비게이션 원칙·상태 문구를 공통 명세로 관리하는 방식이 적절하다.

자동으로 확인 가능한 주요 시나리오:

- 고객 계정이 판매자 앱에 들어오지 못하고 세션·사업장 선택이 제거되는지
- 다른 사업장의 주문·상품을 조회하거나 변경하지 못하는지
- 사업장 등록·선택·로그아웃 시 로컬 상태가 올바르게 바뀌는지
- 주문의 접수 → 준비 → 준비 완료 → 완료와 거절 상태 전이가 올바른지
- 품절·고객 앱·QR 웹 판매 상태가 보존되는지
- 전체 사업장과 선택 사업장 매출이 섞이지 않는지
- 판매자 웹의 주문·환불·상품·옵션·QR·매출·스토어·관리자 UI 계약

Docker는 현재 꺼져 있다. 위 자동 테스트는 Docker 없이 통과했지만, MySQL·Spring·웹·앱을 동시에 사용하는 교차 채널 E2E에는 통합 스택을 다시 켜야 한다.
