# POPQ 외부 연동 과제

외부 계정, 계약, 키 또는 운영 정책이 필요한 작업을 기능 구현과 분리해 유지한다. 준비되지 않은 비밀값을 저장소에 커밋하지 않는다.

| 과제 | 범위 | 현재 상태 | 시작 조건 |
|---|---|---|---|
| 과제 1 | Firebase/OAuth/FCM 실제 연결 | REST 알림·딥링크 기반 완료, 외부 설정 대기 | dev/stage/prod Firebase 프로젝트, Android/iOS 앱 등록, 서버 서비스 계정, 로그인 공급자 결정 |
| 과제 2 | 실제 결제 사업자 | TestPaymentProvider 사용 중 | PG 계약, 결제·취소·환불 정책, 모바일 SDK 결정 |
| 과제 3 | 리뷰 이미지 저장소·검수 | 텍스트 리뷰 완료 | 오브젝트 스토리지, 업로드 제한, 리사이징·검수·삭제 정책 |
| 과제 4 | 공지·정산 등 2차 기능 | 미착수 | 운영 주체, 정산 기준, 회계·세무 요구사항 확정 |

## 과제 1 유지 범위

현재 구현:

- 백엔드 기기 토큰 등록·해제
- 주문 알림 내역·읽음 상태
- `PushNotificationGateway` 추상화
- 소비자 알림 배지·알림함·주문 딥링크

외부 설정 이후 작업:

- Firebase Admin 기반 실제 FCM 송신
- 소비자·판매자 앱 Firebase Messaging 토큰 자동 등록
- 포그라운드·백그라운드·종료 상태 메시지 처리
- Firebase Authentication ID Token과 Spring Access/Refresh Token 교환
- 개발·스테이징·운영 프로젝트와 앱 서명 분리 검증

## 판매자·소비자 계정 경계

- `users.email`은 전역 유일하고 한 사용자는 하나의 `PlatformRole`만 가진다.
- 동일 이메일을 다른 역할로 재등록하면 `DUPLICATE_USER`로 차단한다.
- 판매자 API는 JWT `SELLER` 역할과 활성 스토어 멤버십을 함께 확인한다.
- 소비자·판매자 앱은 서로 다른 application ID/bundle ID를 사용한다.
- 판매자 앱은 전용 보안 세션 키를 사용하고 앱 시작 시 서버 역할을 다시 검증한다.
- 역할 불일치·로그아웃 시 판매자 세션과 선택 스토어 ID를 동시에 제거한다.
- 판매자 주문 조회·동기화·상태 변경은 선택 스토어 ID를 항상 경로에 포함하고 서버의 활성 StoreMember 검증을 통과해야 한다.
